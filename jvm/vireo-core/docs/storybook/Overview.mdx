# JVM Core

`vireo-core` provides the Spring Boot foundation shared by Vireo's JVM modules: managed CRUD mechanics, auditing, search, stable API errors, optional-module SPIs, and isolated migrations.

## Why it exists

Backend aggregates otherwise repeat transaction boundaries, mapper/repository wiring, soft-delete visibility, keyword search, audit publication, error mapping, and migration coordination. Core centralizes those cross-cutting invariants while leaving domain models, business validation, controllers, authorization policy, and consumer-owned schema in the application.

## Installation

```groovy
dependencies {
    implementation platform("com.vireocode:vireo-bom:0.2.0")
    implementation "com.vireocode:vireo-core"
}
```

Auth, History, Query Engine, and Offline already depend on Core. Install it directly when an application wants the base service contracts without another Vireo JVM artifact.

## Ownership boundary

Core owns:

- `BaseEntity`, `BaseMapper`, `BaseRequestMapper`, `SearchableRepository`, `EntityConfig`, and service lifecycle mechanics;
- stable `ApiError` responses and request utilities;
- JPA auditing and method-security enablement required by Starter contracts;
- module-isolated Flyway orchestration;
- SPIs implemented by optional Vireo modules.

Applications own:

- domain entities, DTOs, repositories, controllers, and business rules;
- endpoint and record-level authorization;
- application migrations and database selection;
- workflows that do not fit a conventional CRUD lifecycle.

The dependency auto-configures replaceable defaults for `Clock`, `ObjectMapper`, JSON mappers, auditing, error handling, and Flyway coordination. Consumer beans of the same type take precedence.

## Configuration defaults

```properties
vireo.starter.core.expose-internal-error-details=false
vireo.starter.core.system-auditor=system
```

Unexpected exceptions are logged server-side. Their class and message remain out of HTTP responses unless the application explicitly opts in for a trusted development environment.

Known routing, input, and persistence failures preserve safe client semantics: missing resources are 404, unsupported methods/media types are 405/415, invalid arguments are 400, and integrity or optimistic-lock conflicts are 409.

## Contract behavior

- Soft-deleted entities are hidden consistently from list, get, update, and delete operations.
- History-enabled entities fail before persistence when no history recorder exists.
- Filter payloads fail explicitly when Query Engine is absent.
- Public CRUD entry points cannot be overridden; protected template hooks preserve the lifecycle.
- New endpoints use `BaseRequestService<ID, DOMAIN, CREATE, PATCH, RESPONSE>`: `CREATE` and `PATCH` only contain writable fields, while `RESPONSE` owns read-only and relation display fields.
- Error bodies include stable uppercase-snake-case codes. Throw `ApplicationException` only with a deliberately safe client message.
- Public pagination is bounded to page 10,000, 200 rows per page, and 256 search characters; `rowsPerPage=-1` is rejected rather than expanded into an unbounded query.
- Anonymous Spring Security authentication is never treated as an application principal.

The module README is the complete conceptual guide; generated Javadocs remain the detailed type reference.
